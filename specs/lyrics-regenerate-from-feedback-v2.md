# Spec: Regenerate Lyrics from User Feedback (v2)

Status: ready-for-agent
Supersedes: specs/lyrics-regenerate-from-feedback-v1.md (plan review 2026-09-24: verified ~33 codebase claims; v2 fixes 2 factual errors, closes 1 implementation gap, and widens scope to webapp + Android consumers per user decision).
Design session: grilled 2026-09-24 (8 questions, 3 rounds); plan review 2026-09-24 (3 parallel codebase verifications + 4 clarifying decisions + 5 advisory corrections). Glossary: CONTEXT.md "Lyrics Feedback", "Lyrics", "Recording". Governing ADRs: docs/adr/0007-lyrics-feedback-is-advisory.md (feedback is advisory; regeneration never auto-resolves), docs/adr/0008-gap-placeholders-inserted-post-llm.md (one of the pipeline fixes motivating regeneration).

## Problem Statement

Users report broken Lyrics through Lyrics Feedback (CONTEXT.md): per-user happy/sad with a fixed reason vocabulary (`missing` | `timing` | `wrong_text` | `other`), stored unresolved in `lyrics_feedback` until an admin acts. Meanwhile the LRC generation pipeline has had several fixes that apply to *previously generated* Lyrics — a strict requirements block in the LLM correction prompt (`e9f14ef1`), a grounded zh worked example in the correction prompt (`5d08762a`), and gap placeholders for long instrumental passages (`0c7534b1`, ADR-0008). Recordings generated before these fixes still carry the old defects.

Today, re-fixing those recordings means hand-assembling the documented pipe

```
sow-admin lyrics feedback list --rating poor --format ids | sow-admin lyrics generate --force --stdin
```

and that pipe is broken in three ways:

1. **Wrong selection**: `--rating poor` matches recordings with *any* sad row — even fully resolved ones — as long as one open row of any rating exists (`commands/lyrics.py:131-138`: the rating clause is bare `f.rating = %(rating)s` with no `resolved_at` filter; the `HAVING COUNT(*) FILTER (WHERE f.resolved_at IS NULL) > 0` only requires an open row of any rating). Resolved complaints get needlessly regenerated.
2. **Fire-and-forget**: `--wait` is rejected with `--stdin` (`commands/lyrics.py:368-370`), so after submission nothing updates `recordings.r2_lrc_url` / `lrc_status='completed'` when jobs finish. The batch silently leaves pipeline state in `processing`.
3. **Ambiguous targeting**: feedback points at a Recording (`recording_content_hash`); `lyrics generate` submits by song_id via `get_recording_by_song_id`, a `SELECT ... WHERE song_id = %s AND deleted_at IS NULL` with no `ORDER BY` (`db/client.py:684-694`). For a multi-recording song the regeneration target is nondeterministic and may not be the recording users complained about. Additionally, `--format ids` emits a bare `hash_prefix` for songless recordings (`commands/lyrics.py:172-176`), which `generate` cannot consume at all. (Song-id dedup is already handled — the ids formatter tracks a `seen` set at `commands/lyrics.py:169-177` — so a multi-recording song with sad rows on several recordings is emitted once.)

## Solution

Harden the existing pipe — no new command. The flow remains:

```
sow-admin lyrics feedback list --rating poor --format ids | sow-admin lyrics generate --force --stdin --wait
```

with five changes:

1. **Selection tightening** in `lyrics feedback list`: `--rating poor` yields exactly "recordings with ≥1 open sad row" (any reason — all sad reasons qualify; sad wins over happy, so mixed recordings are included). The `--format ids` hash_prefix fallback is removed; songless recordings are reported to stderr as skipped instead of emitted. (`--format ids` already dedupes song ids via a `seen` set — no change needed there; a regression test pins the behavior.)
2. **Pre-flight target guard** in `lyrics generate --stdin`: for each piped song id, the command queries `lyrics_feedback` itself (it already holds a `ConnectionProvider` via `get_db_client`) for the open-sad `recording_content_hash` values attached to that song's recordings, performs the exact `get_recording_by_song_id` lookup the submission will use, and compares the target's `content_hash`. No open-sad feedback hash matches the target → the song is *skipped* and listed in the run report (never silently regenerating a recording users didn't complain about). `--format ids` stays single-column; no pipe-format change.
3. **Batch wait mode**: `--wait` becomes valid with `--stdin`. `submit_lrc_batch` is changed to **return** the submitted `(song_id, content_hash, job_id)` triples instead of discarding them. After submission, the command polls every job to completion reusing the `audio batch` machinery (the unified interleaved poll loop `_process_batch` / `_poll_one_cycle`, service-first + R2-fallback reconciliation — see `specs/batch-unified-poll-loop-v2.md`), then reconciles `recordings` (`r2_lrc_url`, `lrc_status='completed'`, `lrc_source`) per recording. A run manifest (same `{batch_id}_manifest.json` convention as `audio batch`; new writer/reader shaped for this flow) records song ids, content hashes, job ids, and outcomes; the new `--resume <manifest>` flag re-polls an interrupted run without resubmitting; Ctrl+C triggers the same `_reconcile_on_interrupt` semantics as `audio batch`. With `--stdin`, the batch path is taken **regardless of id count** — a 1-id pipe gets the guard, manifest, poll loop, and report exactly like a 100-id pipe.
4. **End-of-run report**: per-recording outcome (completed / failed / skipped-guard / skipped-songless), failures with job ids, and the exact `sow-admin lyrics feedback resolve <song-id>` commands for the recordings the admin judges fixed. Nothing is auto-resolved (ADR-0007).
5. **Visibility demotion + consumer widening**: completed regenerations demote `visibility_status` to `'review'` (the human-verified checkmark is withdrawn pending spot-check), **and** every consumer surface that currently pins `'published'` is widened to also serve `'review'`, so a demoted song never disappears for end users (Story 11): the webapp signed-url endpoint, the webapp transitions/preview endpoint, the webapp song-detail endpoint, and the Android app's song list/search filters. Accepted consequence (user decision 2026-09-24): Android has no badge concept — presence in the app *is* its only verification signal — so widening makes "human-verified" a webapp-badge-only concept, and the app will show all never-verified `'review'` recordings (the live catalog is ~218 `review` / 0 `published`, so a published-only Android app lists almost nothing today regardless).

Regeneration uses plain `--force` only. The fixed bugs are all downstream of transcription (LLM correction prompt + post-LLM gap placeholders), and the cache structure guarantees they take effect: the YouTube transcript path re-fetches and re-runs LLM correction on every job (`youtube_transcript.py:1069-1071`; no transcription cache), the LRC result cache is bypassed by `options.force` (`queue.py:1413-1414`; key is content_hash + lyrics + language + static `lrc-lang-v5` tag, `queue.py:51-66`), and the Qwen3 ASR cache keys include `SOW_DASHSCOPE_ASR_CACHE_VERSION` so prompt/context changes invalidate automatically (`workers/lrc.py:705-721`, `config.py:236`). `--force-qwen3-asr` (paid re-transcription) is **not** part of this flow.

## User Stories

1. As an admin, I want one pipe that regenerates every recording users are currently complaining about, so that fixed pipeline bugs reach old recordings without hand-built song lists.
2. As an admin, I want `--rating poor` to mean "has unresolved negative feedback", so that I never spend regeneration cost on recordings whose complaints were already resolved.
3. As an admin, I want all sad reasons to qualify (missing, timing, wrong_text, other), so that prompt and gap-placeholder fixes reach every complaint class they might repair.
4. As an admin, I want recordings with both happy and sad open feedback to be regenerated (sad wins), so that one dissatisfied user's report isn't vetoed by another's praise.
5. As an admin, I want songless recordings and multi-recording-song mismatches skipped and reported — never silently targeted — so that the run report is trustworthy.
6. As an admin, I want `--wait` to work in batch mode, so that `recordings.lrc_status` / `r2_lrc_url` reflect reality when the run ends instead of being stuck at `processing`.
7. As an admin, I want a run manifest, so that I can audit what was attempted and resume after interruption.
8. As an admin, I want Ctrl+C to leave pipeline state consistent, so that a cancelled run doesn't strand recordings.
9. As an admin, I want `--dry-run` to print the selection and guard results without submitting, so that I can review scope before spending API quota.
10. As an admin, I want completed regenerations demoted to `visibility_status='review'`, so that the human-verified checkmark is withdrawn until I spot-check.
11. As a worship participant, I want a demoted (under-review) recording to keep working everywhere — webapp browse/search/favorites/detail, playback and share signed URLs, transitions preview, and the Android app — so that regeneration never makes a song disappear; only the verified badge is withdrawn.
12. As an admin, I want the run report to print the exact `lyrics feedback resolve` commands per fixed recording, so that resolution stays my explicit judgment (ADR-0007) with zero lookup friction.
13. As an admin, I want unresolved feedback to be regenerated again on the next run, so that future pipeline fixes automatically retry still-broken recordings (runbook discipline: resolve after review).
14. As a worship participant, I want the canonical Lyrics of a song I reported to improve, so that my next session benefits.

## Implementation Decisions

- **No new command, no schema change, no new glossary terms, no new ADR.** The feature is a hardening of `lyrics feedback list` + `lyrics generate`, plus visibility-consumer widening in webapp + Android; ADR-0007/0008 already govern the surprising decisions. (The `'review'` visibility value already exists — `_VALID_VISIBILITY_STATUSES = {"published", "review", "hold"}`, `db/client.py:35` — and is already served by webapp browse/search/favorites; this spec extends that treatment to the remaining published-only surfaces rather than introducing a new state.)
- **Selection tightening (`lyrics feedback list`)**: the `--rating` clause gains the open-only filter — `f.rating = %(rating)s` becomes `f.resolved_at IS NULL AND f.rating = %(rating)s`. **No `HAVING` change**: the WHERE filters rows before grouping, so with `--rating poor` every surviving group already consists solely of open sad rows and the existing generic `HAVING COUNT(*) FILTER (WHERE f.resolved_at IS NULL) > 0` is sufficient (a stricter sad-specific HAVING would be redundant). Behavior change: recordings whose sad rows are all resolved but which have an open happy row drop out of `--rating poor` — that is the intent. Table-output consequence (accepted): with `--rating` given, the aggregate columns count only rows matching the rating filter — under `--rating poor`, `open_count` counts open sad rows only and `open_happy` is always 0 (a recording with 3 open sad + 2 open happy shows 3, and the 👍 indicator never appears). Without `--rating`, table output is unchanged.
- **`--format ids` fallback removal**: rows whose recording has no `song_id` are no longer emitted as bare `hash_prefix`; they are collected and printed to stderr as a skipped list (Rich stderr console), keeping stdout a clean, fully-consumable id stream. No dedup change: the ids formatter already emits each target once via a `seen` set (`commands/lyrics.py:169-177`) — Seam 1 gains a regression assertion that a multi-recording song yields a single id.
- **Feedback-aware pre-flight guard (DB-lookup, not pipe-format)**: in `lyrics generate --stdin`, each piped song id is checked before submission: query `lyrics_feedback` (joined via `recordings.song_id`) for the open-sad `recording_content_hash` values on that song, run the identical `get_recording_by_song_id` lookup `submit_lrc_single` will use (`db/client.py:684-694`, including its `deleted_at IS NULL` predicate), and compare the returned recording's `content_hash` against the feedback hashes. No match → skip the song and record it as `skipped-guard` (with both the target hash and the feedback hashes) in the report. A song id with no open-sad feedback at all (e.g. piped from somewhere other than `feedback list`) passes the guard unconditionally — the guard only vetoes *mismatched* targeting, it does not police where ids came from. Rationale for skip-over-warn: the lookup has no `ORDER BY`, so a warned-but-submitted run could regenerate a different recording's Lyrics while the report reads clean. Pinning `ORDER BY imported_at DESC` is rejected — the feedback's recording is not necessarily the newest. The content hash is deliberately **not** carried through the pipe: the shared stdin reader (`services/prompts.py:14-25`), its duplicate (`catalog.py:451-460`), and the inline `sys.stdin.read().splitlines()` copies in `audio.py` (:1958, :3011, :3362) all treat each whole line as an id, so a second column would corrupt every existing pipe consumer (`audio.py` download/delete/set-visibility/sync-components/batch, `lyrics.py` generate/align/view).
- **`submit_lrc_batch` returns submissions**: change `services/lrc_jobs.py:201` from `-> None` to returning `list` of submitted `(song_id, content_hash, job_id)` triples (skipped/errored songs are not included; the existing printed summary is unchanged). Only caller is `commands/lyrics.py:420`; the test double in `tests/admin/test_lyrics_generate_commands.py:50` is updated. This is the mechanism that gives batch `--wait` its job ids without changing the pipe format.
- **`--stdin` always takes the batch path**: today `lyrics_generate` routes on `len(song_ids) == 1` (`commands/lyrics.py:406-420`) — a 1-id pipe would land in `submit_lrc_single(wait=wait)`, i.e. the 600s `wait_for_completion` path with no guard, no manifest, and no run report. Change the routing to `if stdin: <batch flow> elif single positional id: submit_lrc_single(...)`. The guard and `--dry-run` run on stdin input before submission regardless of count; the single-song shortcut (with its per-job 600s wait) remains only for the positional-argument form `lyrics generate <song-id>`, which is unchanged by this spec. `--resume` therefore only ever describes batch runs.
- **Batch `--wait`**: lift the `--stdin` + `--wait` rejection (`commands/lyrics.py:368-370`; leave the identical check in `lyrics align` at :704-705 untouched — align stays fire-and-forget). After `submit_lrc_batch` returns, poll all submitted job ids via the `audio batch` unified poll machinery — `_process_batch` (`audio.py:7627`) driving `_poll_one_cycle` (`audio.py:7410`), service-first + R2-fallback reconciliation per `specs/batch-unified-poll-loop-v2.md`. Do not use the single-song `wait_for_completion` (its 600s timeout at `lrc_jobs.py:166-167` is per-job and wrong for a batch). On per-job completion: `update_recording_lrc(hash_prefix, r2_lrc_url=..., visibility_status='review', lrc_source=...)` — identical to single-song waited completion (`lrc_jobs.py:189-193`); the explicit `'review'` kwarg is required because `update_recording_lrc` otherwise promotes NULL→`'published'` (`db/client.py:1248` COALESCE). On failure: `lrc_status='failed'`, recorded with the job id in the manifest and report. The Analysis Service serializes YouTube transcript calls (max 1 concurrent, ≥3s interval — `config.py:333-343`) and caps Qwen3 ASR at 2 concurrent (`config.py:235`, `queue.py:205`), so large batches are slow; the poll loop must have no fixed overall timeout (poll until all jobs settle, like `audio batch`).
- **Manifest and resume**: same `{batch_id}_manifest.json` convention as `audio batch` (spec `scale-key-bpm-analysis-batch-v4.md`, `_write_manifest` at `audio.py:5868`): song ids, content hashes, job ids, per-job outcome, started/finished timestamps. This is an **adaptation, not drop-in reuse** — `_write_manifest`/`_resume_from_manifest` (`audio.py:8018`) are shaped around audio-batch's `(song_id, step)` active-jobs dict and download futures; the lyrics flow gets its own writer/reader following the same convention. New flag `--resume <manifest>`: re-attaches to the recorded job ids and re-enters the poll loop without resubmitting; mutually exclusive with `--stdin` and `--dry-run` (a resumed run always waits — it is a poll continuation, and `--force` was already applied at original submission). Ctrl+C runs `_reconcile_on_interrupt` (`audio.py:7891`) semantics: jobs already submitted stay valid server-side (WAITING-status recovery per `waiting-status-for-fire-and-forget-jobs-v1.md`); the manifest is flushed before exit so `--resume` can finish the run.
- **`--dry-run`** (new flag): performs selection and the pre-flight guard, prints the would-be submission set plus skips, submits nothing, writes no manifest. Mutually exclusive with `--resume`.
- **Visibility demotion + consumer widening** (user decision 2026-09-24): batch completion demotes `visibility_status` to `'review'`, matching single-song waited mode — **and** the published-only consumer surfaces are widened so Story 11 holds on every client:
  - **Webapp — widen (serve `'review'` too)**:
    - `src/app/api/signed-url/shared-handler.ts:94`: `eq(recordings.visibilityStatus, "published")` → `inArray(..., ["published", "review"])` (playback/share signed URLs keep working for demoted recordings).
    - `src/app/api/transitions/preview/route.ts:62`: same widening (transition preview keeps working).
    - `src/app/api/songs/[id]/route.ts:20` + `src/lib/db/songs.ts:360-366`: `getSong` currently takes a single string and uses `eq()`; widen its signature to `string | string[]` (the file already has `inArray`-based helpers, e.g. `recordingVisibilityPredicate` at songs.ts:200-210) and have the route pass `["published", "review"]`, so a demoted song's detail page does not 404/empty out.
  - **Webapp — deliberately NOT widened**: `SongCard.tsx:92-94` `isVerified` badge (that checkmark is exactly what demotion withdraws) and the published-preference-then-fallback primary-recording picks (`SongCard.tsx:77-80`, `lib/db/songs.ts:120-122`), which already fall back to `recordings[0]`.
  - **Enumeration completeness**: an audit of every `"published"` occurrence in `src/app/api/` confirms the three widen sites above are the only published-pinned API surfaces — browse (`songs/route.ts:77-78`), search (`search/route.ts:46-47`), and semantic (`semantic/route.ts:90`) already default to `["published","review"]`, favorites/dashboard query with `["published","review"]` (`dashboard.ts:92,154`), and no recordings-by-id or download route pins `'published'`.
  - **Android — widen**: `SongsApi.kt:16,28` default `visibilityStatus` `"published"` → `"published,review"`; `SongsRepository.kt:37,52` explicit `"published"` → `"published,review"`; client-side `publishedOnly()` (`SongsRepository.kt:65-70`) and `SongModels.kt:49-50` `publishedRecordings` filter (`null || "published"`) widened to include `"review"` — rename `publishedRecordings` → `visibleRecordings` (LSP rename across `SongsetsScreens.kt:546-553`, `SongsetsViewModels.kt:396,416`, `SongsRepository.kt`) so the name stops lying. Update `README.md:157-159` ("Source recording previews require published recordings…") to say published-or-review.
  - Semantic search needs no server change (webapp semantic route already defaults to `["published","review"]`; Android semantic results flow through the widened client-side filter).
- **Cache depth**: submit with `force=True` only. Do not pass `--force-qwen3-asr` / `--no-whisper-cache` in this flow; the motivating fixes (`e9f14ef1`, `5d08762a`, `0c7534b1`) are downstream of transcription and plain `--force` picks them up (see Solution). `--force-qwen3-asr` remains a manual per-song escalation for admins who suspect a bad cached ASR transcription.
- **Idempotency is runbook discipline**: no persisted dedup state (no `regenerated_at` column, no runs table). Unresolved feedback is deliberately re-regenerated on the next run — a free retry after future pipeline fixes. Admins resolve via `lyrics feedback resolve` after reviewing a run (ADR-0007).
- **No auto-resolve, no pipeline-state coupling from feedback**: selection reads `lyrics_feedback`; nothing ever writes `resolved_at` except `lyrics feedback resolve/unresolve` (`commands/lyrics.py:287-329`; both accept a recording content hash OR a song id), and feedback never mutates `recordings.lrc_status` (ADR-0007).
- **Overwrite safety is inherited**: regeneration overwrites `{hash_prefix}/lyrics.lrc` via `upload_official_lrc`, which backs up the previous object (5 retained, `MAX_BACKUPS_PER_PREFIX` at `r2.py:23`) with ETag stale protection (`StaleObjectError`, `r2.py:347-444`). No additional rollback machinery in this spec.

## Testing Decisions

- **Good tests assert external behavior only**: CLI stdout/stderr and database end-state given a real (testcontainers) Postgres and a mocked AnalysisClient; HTTP status + response shape for webapp route tests; repository-level request paths and filtering for Android tests. No assertions on SQL text or internal call wiring.
- **Seam 1 — `lyrics feedback list` selection (admin CLI integration, `CliRunner` + testcontainers; prior art `tests/admin/test_audio_commands.py` with the pgvector/pg16 fixture in `tests/conftest.py:26-30`)**: seed feedback rows covering the matrix — open sad only; resolved sad + open happy (must drop out of `--rating poor`); open happy only; open sad + open happy (included, sad wins); per-reason coverage including `timing` and `other`. Assert `--format ids` stdout contains exactly the qualifying song ids — including a regression assertion that a song with open sad rows on two recordings appears exactly once (pinning the existing `seen`-set dedup) — and songless recordings appear only in the stderr skip list.
- **Seam 2 — pre-flight guard**: seed a song whose feedback's `recording_content_hash` belongs to a different recording than the one generation would target; assert the song is skipped, appears in the report as `skipped-guard`, and no job is submitted for it. A song whose target recording matches an open-sad feedback hash → submitted normally. A piped song id with no feedback rows at all → passes the guard.
- **Seam 3 — batch `--wait` end-state**: mocked AnalysisClient driving jobs through pending → completed/failed; assert `recordings` rows end at `lrc_status='completed'` + `r2_lrc_url` + `lrc_source` + `visibility_status='review'` for successes, `lrc_status='failed'` for failures, manifest contents record job ids and outcomes, and `--resume` re-polls without resubmitting (assert the mocked submit path is not called on resume). Assert `lyrics_feedback.resolved_at` is untouched throughout. Assert `submit_lrc_batch` returns the submitted triples (contract the poll loop depends on).
- **Seam 4 — flag validation + routing**: `--wait` accepted with `--stdin`; `--dry-run` submits nothing and writes no manifest; `--resume` rejects `--stdin`/`--dry-run`; a `--stdin` pipe carrying exactly one id takes the batch path (guard runs, manifest written, report printed — the single-song `submit_lrc_single` path is not invoked), while `lyrics generate <song-id>` without `--stdin` keeps single-song mode.
- **Seam 5 — webapp consumer widening (vitest; extend existing route tests)**: `src/test/api/signed-url/route.test.ts` and `src/test/api/transitions/preview.test.ts` gain a case where the recording is `'review'` and the request succeeds; `src/test/api/songs/[id].test.ts` gains a case where a song whose only recording is `'review'` still returns the song. Badge behavior is unchanged — no new `SongCard` assertions beyond what exists.
- **Seam 6 — Android consumer widening (Robolectric/unit; extend `SongsRepositoryTest.kt`)**: request paths now carry `visibilityStatus=published%2Creview`; a response mixing `published` and `review` recordings keeps both (the existing `draft`-exclusion case stays green).
- No analysis-service changes exist in this spec, so no service-side tests.

## Out of Scope

- Scheduling (cron / CI) or event-driven triggering — the run is admin-invoked (ADR-0007: triage stays in the Admin CLI).
- Sweeping `lrc_status='failed'` or missing-Lyrics recordings without feedback — already served by `audio batch --lrc-status failed --generate-lyrics --force`.
- Automating the `timing`→re-align or `wrong_text`/`other`→manual-review actions from the triage queue's suggested-action mapping; this spec automates regeneration only, and all sad reasons are eligible because the shipped fixes plausibly repair more than `missing`.
- Persisted regeneration bookkeeping (dedicated runs table or `lyrics_feedback` columns) — runbook discipline chosen in grilling; revisit only if triage discipline lapses in practice.
- `--force-qwen3-asr` / `--no-whisper-cache` in the default flow (paid re-transcription; manual escalation only).
- Content-hash-targeted submission (regenerating a specific recording of a multi-recording song). Mismatches are skipped and reported instead; a content-hash submit path is future work if the catalog grows real multi-recording songs.
- Widening the `isVerified` badge or primary-recording preference to treat `'review'` as verified — the badge withdrawal is the point of demotion.
- Render-worker and analysis-service changes.
- CONTEXT.md glossary additions and new ADRs (nothing here is a new domain term or a hard-to-reverse trade-off beyond what ADR-0007/0008 already record).

## Further Notes

- The sibling spec `specs/collect_user_lyrics_feedback.md` owns the collection half of this feature and the house format this spec follows. Its suggested-action mapping is presentation-only; this spec is the first consumer to *act* on a mapping, and deliberately broadens it (all sad reasons regenerate) because the motivating fixes span the correction prompt and gap placeholders, not just missing-Lyrics generation.
- Motivating fixes and why plain `--force` suffices: `e9f14ef1` (strict requirements block in the LLM correction prompt), `5d08762a` (grounded zh worked example in the correction prompt), `0c7534b1` (gap placeholders, YouTube path, ADR-0008). The YouTube path re-fetches the transcript and re-runs correction on every job (`youtube_transcript.py:1069-1071`); the LRC result cache is keyed on content_hash + lyrics + language (+ static `lrc-lang-v5` tag) and is bypassed by `options.force` (`queue.py:1413-1414`); the Qwen3 ASR cache self-invalidates via `SOW_DASHSCOPE_ASR_CACHE_VERSION` (`workers/lrc.py:705-721`, `config.py:236`).
- Throughput expectation: YouTube transcript fetching is serialized (1 concurrent, ≥3s apart) and Qwen3 ASR is capped at 2 concurrent, so a large feedback queue produces a long-running batch. The manifest + `--resume` + Ctrl+C reconciliation exist precisely so a multi-hour run is survivable; do not add concurrency controls in this spec.
- Pipe-format stability: `--format ids` stays one song id per line. The guard gets its content hashes from a direct `lyrics_feedback` query inside `lyrics generate`, not from the pipe, because the shared stdin readers (`services/prompts.py:14-25`, `catalog.py:451-460`) and the inline stdin copies (`audio.py:1958`, `:3011`, `:3362`) treat each whole line as an id — any extra column would be handed to the analysis service as a bogus song id across every existing pipe consumer.
- v1 → v2 delta (from plan review + second-pass advisory review): fixed Out-of-Scope flag (`--lrc` → `--generate-lyrics`); closed the batch-`--wait` job-id gap (`submit_lrc_batch` returned `None`); declared `--dry-run`/`--resume` as new flags with conflict rules; forced `--stdin` onto the batch path regardless of id count (a 1-id pipe previously hit the 600s single-song path with no guard/manifest/report); demotion now paired with webapp + Android consumer widening after verification showed `'review'` was invisible to Android and rejected by signed-url/transitions/song-detail endpoints — with the accepted consequence that human-verified status becomes a webapp-badge-only concept (Android has no badge; live catalog is ~218 review / 0 published); documented that `--format ids` already dedupes (no change; regression-pinned) after the v2 draft briefly claimed otherwise; narrowed the selection fix to the WHERE clause only (a sad-specific HAVING would be redundant) and recorded the table-count consequence of rating-filtered aggregation; corrected line references (`lyrics.py:368-370`, `queue.py:1413-1414`, `youtube_transcript.py:1069`, `lrc_jobs.py:189-193`, `client.py:684-694` incl. `deleted_at IS NULL`); noted `lyrics view` (not "preview") among stdin consumers and that three audio commands use inline stdin copies.
