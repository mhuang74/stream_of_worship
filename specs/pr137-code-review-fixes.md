## Issue 1 — Migration 0019 fails in production

### Severity: Critical (blocks deployment)

### Files

- `delivery/webapp/drizzle/0019_plain_secret_warriors.sql` (new in PR)
- `delivery/webapp/drizzle/0018_theme_anchors.sql` (already in main)
- `delivery/webapp/src/db/schema.ts:339-354`

### Problem

Migration 0018 (`0018_theme_anchors.sql`) — already merged to main — creates the `theme_anchors` table and a correct HNSW cosine index:

```sql
-- 0018 (hand-written, already in main)
CREATE TABLE IF NOT EXISTS theme_anchors (
    theme         TEXT PRIMARY KEY,
    embedding     vector(1536) NOT NULL,
    model_version TEXT NOT NULL DEFAULT 'text-embedding-3-small',
    created_at    TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS idx_theme_anchors_embedding_cosine
    ON theme_anchors USING hnsw (embedding vector_cosine_ops);
```

Migration 0019 (`0019_plain_secret_warriors.sql`) — generated by `drizzle-kit generate` in this PR — emits two conflicting statements:

```sql
-- 0019 line 1 — no IF NOT EXISTS, table already exists from 0018
CREATE TABLE "theme_anchors" (
    "theme" text PRIMARY KEY NOT NULL,
    "embedding" vector(1536) NOT NULL,
    "model_version" text DEFAULT 'text-embedding-3-small' NOT NULL,
    "created_at" timestamp with time zone DEFAULT now()
);
--> statement-breakpoint
-- ... ALTER TABLE statements for recordings/songs (these are fine) ...
--> statement-breakpoint
-- 0019 line 20 — btree + vector_cosine_ops is invalid
CREATE INDEX "idx_theme_anchors_embedding_cosine"
    ON "theme_anchors" USING btree ("embedding" vector_cosine_ops);
```

### Failures

**Failure A — `CREATE TABLE "theme_anchors"`:**

PostgreSQL returns `relation "theme_anchors" already exists`. The statement lacks `IF NOT EXISTS` because drizzle-kit generate does not know 0018 already created the table.

**Failure B — `CREATE INDEX ... USING btree (... vector_cosine_ops)`:**

PostgreSQL returns `operator class "vector_cosine_ops" does not exist for access method "btree"`. Drizzle-kit generate emits `USING btree` for any `index().on(...)` declaration. For vector similarity indexes, drizzle-kit has no native HNSW/IVFFlat support.

### Why the schema definition is also wrong

`schema.ts:339-354` declares the index using drizzle's `index().on()` helper, which drizzle-kit always generates as btree:

```typescript
index("idx_theme_anchors_embedding_cosine").on(
    sql`${t.embedding} vector_cosine_ops`
),
```

This is semantically incorrect — vector similarity indexes require HNSW or IVFFlat access methods, not btree. Any future `drizzle-kit generate` will continue to emit broken SQL.

### Impact

`npx drizzle-kit migrate` halts at Failure A and rolls back the entire migration (drizzle runs each migration file in a single transaction). The new columns on `recordings` (`key_algorithm_version`, `key_score_margin`, `key_window_agreement`, `key_candidates`, `key_detected_at`), the new columns on `songs` (`musical_key_root`, `musical_key_mode`, `musical_key_start_root`, `musical_key_end_root`, `musical_key_start_pitch_class`, `musical_key_end_pitch_class`, `musical_key_parse_status`), and the new `idx_songset_items_song_id` index never get applied. The PR's reverse-lookup queries perform full table scans as a side effect.

### Fix

#### Step A: Edit `0019_plain_secret_warriors.sql` directly

Remove the duplicate `CREATE TABLE` and broken index. Keep the column additions and the songset_items index. Result:

```sql
-- 0019_plain_secret_warriors.sql (hand-edited)
ALTER TABLE "recordings" ADD COLUMN "key_algorithm_version" text;--> statement-breakpoint
ALTER TABLE "recordings" ADD COLUMN "key_score_margin" real;--> statement-breakpoint
ALTER TABLE "recordings" ADD COLUMN "key_window_agreement" real;--> statement-breakpoint
ALTER TABLE "recordings" ADD COLUMN "key_candidates" text;--> statement-breakpoint
ALTER TABLE "recordings" ADD COLUMN "key_detected_at" timestamp with time zone;--> statement-breakpoint
ALTER TABLE "songs" ADD COLUMN "musical_key_root" text;--> statement-breakpoint
ALTER TABLE "songs" ADD COLUMN "musical_key_mode" text;--> statement-breakpoint
ALTER TABLE "songs" ADD COLUMN "musical_key_start_root" text;--> statement-breakpoint
ALTER TABLE "songs" ADD COLUMN "musical_key_end_root" text;--> statement-breakpoint
ALTER TABLE "songs" ADD COLUMN "musical_key_start_pitch_class" integer;--> statement-breakpoint
ALTER TABLE "songs" ADD COLUMN "musical_key_end_pitch_class" integer;--> statement-breakpoint
ALTER TABLE "songs" ADD COLUMN "musical_key_parse_status" text;--> statement-breakpoint
CREATE INDEX "idx_songset_items_song_id" ON "songset_items" USING btree ("song_id");
```

#### Step B: Update `schema.ts:339-354` to suppress drizzle-kit's index generation

Remove the `index().on()` declaration from the Drizzle schema and add a comment explaining that the index is managed via raw SQL migration. Keep the table definition so `drizzle-kit push` does not recommend dropping the table:

```typescript
// theme_anchors table (managed by admin CLI's `sow-admin theme-anchors sync`)
// Declared here so drizzle-kit push does not propose dropping it.
// The HNSW cosine index is created by hand-written SQL migration
// (0018_theme_anchors.sql). Drizzle-kit cannot express vector similarity
// indexes (HNSW/IVFFlat) — do not add `index().on()` here; it will be
// mis-generated as `USING btree (... vector_cosine_ops)` which is invalid.
export const themeAnchors = pgTable(
  "theme_anchors",
  {
    theme: text("theme").primaryKey(),
    embedding: vector("embedding", { dimensions: 1536 }).notNull(),
    modelVersion: text("model_version")
      .notNull()
      .default("text-embedding-3-small"),
    createdAt: timestamp("created_at", { withTimezone: true }).defaultNow(),
  },
  // no indexes — managed by 0018_theme_anchors.sql
);
```

#### Step C: Re-generate the snapshot

Run `npx drizzle-kit generate` to produce a corrected `0019_snapshot.json` that matches the edited SQL. Verify `0019_snapshot.json` no longer contains a `CREATE TABLE` for `theme_anchors` and no longer contains a `btree + vector_cosine_ops` index entry.

#### Step D: Verify migration runs clean

```bash
# In a test database that already has 0018 applied:
npx drizzle-kit migrate
# Exit code 0, no errors
```

## Issue 2 — `highlightSongId` URL cleanup races with SongList scroll effect

### Severity: High (feature broken in production)

### Files

- `delivery/webapp/src/app/songsets/[id]/SongsetEditorClient.tsx:115-161`
- `delivery/webapp/src/components/songset/SongList.tsx:392-425`

### Problem

The navigation flow:

1. User clicks a songset in `LocateSongsetsPopover`.
2. `router.push('/songsets/<id>?highlightSong=<songId>')` navigates.
3. `SongsetEditorClient` reads `searchParams.get('highlightSong')` into `highlightSongId`.
4. `SongsetEditorClient` passes `highlightSongId` as a prop down to `SongsetEditor` -> `SongList`.
5. `SongList` spins up a `requestAnimationFrame` retry loop to find the DOM element with the matching `data-song-id` attribute, then calls `scrollIntoView` and applies the highlight ring.

The bug lives in `SongsetEditorClient.tsx:155-161`:

```typescript
const highlightSongId = searchParams.get("highlightSong");

useEffect(() => {
    if (!highlightSongId) return;
    const next = new URLSearchParams(searchParams.toString());
    next.delete("highlightSong");
    const query = next.toString();
    router.replace(`/songsets/${songsetId}${query ? `?${query}` : ""}`);
}, [highlightSongId, songsetId, searchParams, router]);
```

The effect calls `router.replace` immediately after mount to strip the param from the URL. After `router.replace` settles, Next.js emits a new `searchParams` object, `SongsetEditorClient` re-renders, `highlightSongId` becomes `null`, the value propagates to `SongList` as a prop, and `SongList`'s effect cleanup fires — cancelling the pending `requestAnimationFrame` and the timeout-based retry loop.

The comment at `SongsetEditorClient.tsx:153` says: "The highlightSongId value is retained in component state via the SongsetEditor prop until the scroll/highlight effect in SongList has run." This is incorrect — `highlightSongId` is not retained in state; it is derived directly from `searchParams`, which changes after `router.replace`.

The race is timing-dependent and will fail intermittently in production depending on:

- Network conditions (router replace latency)
- Songset size (more items = slower DOM render)
- Whether drag-and-drop layout shifts are still settling
- Hydration speed on slow devices

### Fix

Decouple the highlight state from `searchParams` so URL cleanup does not null out the value mid-effect. Two options; implement Option A (smaller blast radius).

#### Option A: Capture `highlightSongId` in local state, run cleanup once (recommended)

```typescript
// SongsetEditorClient.tsx — replacement for lines 115 + 155-161

const highlightSongParam = searchParams.get("highlightSong");
const [highlightSongId, setHighlightSongId] = useState<string | null>(
    highlightSongParam
);

useEffect(() => {
    if (!highlightSongParam) return;
    // Strip ?highlightSong= from the URL while preserving other params.
    const next = new URLSearchParams(searchParams.toString());
    next.delete("highlightSong");
    const query = next.toString();
    router.replace(`/songsets/${songsetId}${query ? `?${query}` : ""}`);
    // Do NOT clear highlightSongId here — let SongList's effect own the
    // highlight lifecycle. Clear it only after SongList is done.
}, [highlightSongParam, songsetId, searchParams, router]);
```

Then add an explicit clear handler, owned by SongList via a callback prop:

```typescript
// SongsetEditorClient.tsx — pass a callback to clear highlight
<SongsetEditor
    ...
    highlightSongId={highlightSongId}
    onHighlightConsumed={() => setHighlightSongId(null)}
/>
```

```typescript
// SongList.tsx — after the highlight ring is shown and dismissed
useEffect(() => {
    if (!highlightSongId) return;
    let raf: number;
    let attempts = 0;
    const maxAttempts = 20;
    let dismissTimer: ReturnType<typeof setTimeout>;

    const tryScroll = () => {
        const el = findSongElement(highlightSongId);
        if (el) {
            el.scrollIntoView({ behavior: "smooth", block: "center" });
            setHighlightedSongId(highlightSongId);
            dismissTimer = setTimeout(() => {
                setHighlightedSongId(null);
                onHighlightConsumed?.();
            }, 3000);
            return;
        }
        if (++attempts < maxAttempts) {
            timeoutId = setTimeout(() => {
                raf = requestAnimationFrame(tryScroll);
            }, 50);
        } else {
            onHighlightConsumed?.();
        }
    };
    // ...rest of effect unchanged...
}, [highlightSongId, onHighlightConsumed]);
```

#### Option B: Store highlight only in a ref, never in URL-derived state

Move the `highlightSongId` into a `useRef` populated once from `searchParams` and never updated by `router.replace`. The trade-off: `?highlightSong=` still appears in the URL until the next full navigation, breaking the ephemeral-param design goal from the v2 spec.

## Issue 3 — `findSongsetsContainingSong` has no `LIMIT` and inefficient CTE

### Severity: Medium (operational / performance)

### Files

- `delivery/webapp/src/lib/db/songsets.ts:140-204`

### Problem

```typescript
const rows = await db
    .with(itemCountSubquery)
    .select({ ... })
    .from(songsets)
    .innerJoin(songsetItems, eq(songsetItems.songsetId, songsets.id))
    .innerJoin(users, eq(users.id, songsets.userId))
    .leftJoin(itemCountSubquery, eq(itemCountSubquery.songsetId, songsets.id))
    .where(and(eq(songsets.userId, userId), eq(songsetItems.songId, songId)))
    .orderBy(desc(songsets.updatedAt));
    // <- No .limit()
```

There is no upper bound on the number of returned rows. If a popular song appears in many of a user's songsets, the response payload and DOM render grow without bound.

Additionally, the `item_counts` CTE scans the entire `songset_items` table (no `userId` filter), computing counts for every songset in the database even though only the current user's songsets are returned:

```typescript
const itemCountSubquery = db
    .$with("item_counts")
    .as(
        db
            .select({
                songsetId: songsetItems.songsetId,
                count: sql`count(${songsetItems.id})::int`.as("count"),
            })
            .from(songsetItems)
            .groupBy(songsetItems.songsetId)
            // <- no user filter, crosses all users
    );
```

The `LEFT JOIN` filters the CTE output down to the returned rows, so no data leaks, but the CTE itself runs an unbounded group-by across all songset_items.

Mitigating factors:

- The query is scoped by `userId` in the outer `WHERE`, so cross-user results are not returned.
- The popover already scrolls when results overflow `--available-height`.

### Fix

Add a defensive `LIMIT` (suggest 50 — more than any realistic single-user songset count, but caps pathological cases) and scope the CTE to the user's songsets so the planner can use indexes effectively:

```typescript
const itemCountSubquery = db
    .$with("item_counts")
    .as(
        db
            .select({
                songsetId: songsetItems.songsetId,
                count: sql`count(${songsetItems.id})::int`.as("count"),
            })
            .from(songsetItems)
            .innerJoin(songsets, eq(songsets.id, songsetItems.songsetId))
            .where(eq(songsets.userId, userId))
            .groupBy(songsetItems.songsetId)
    );

const rows = await db
    .with(itemCountSubquery)
    .select({ ... })
    .from(songsets)
    .innerJoin(songsetItems, eq(songsetItems.songsetId, songsets.id))
    .innerJoin(users, eq(users.id, songsets.userId))
    .leftJoin(itemCountSubquery, eq(itemCountSubquery.songsetId, songsets.id))
    .where(and(eq(songsets.userId, userId), eq(songsetItems.songId, songId)))
    .orderBy(desc(songsets.updatedAt))
    .limit(50);
```

## Issue 4 — `globalThis.CSS.escape` has no fallback

### Severity: Medium (resilience)

### Files

- `delivery/webapp/src/components/songset/SongList.tsx:400-402`

### Problem

```typescript
const el = document.querySelector(
    `[data-song-id="${globalThis.CSS.escape(highlightSongId)}"]`
);
```

`CSS.escape` is widely supported in modern browsers (Chrome 46+, Firefox 31+, Safari 10+), but:

- Older Android WebView versions (< 46) lack `CSS.escape`.
- Some embedded browsers (e.g., older Kindle browsers, Tizen TV webviews) lack it.
- The Android app uses the system WebView, which varies by OEM and OS version.

If `CSS.escape` is undefined, the line throws `TypeError: Cannot read properties of undefined (reading 'escape')`. The error propagates up, the effect cleanup never schedules the retry, and the user silently sees no scroll/highlight. No error visible to the user; the feature just does nothing.

### Fix

Add a safe wrapper that falls back to a regex-based escaper when `CSS.escape` is unavailable:

```typescript
function escapeCssSelectorValue(value: string): string {
    if (typeof CSS !== "undefined" && typeof CSS.escape === "function") {
        return CSS.escape(value);
    }
    // Fallback for older webviews: escape backslash and double-quote,
    // which are the only characters that can break out of a quoted
    // CSS attribute selector.
    return value.replace(/["\\\\]/g, "\\\\$&");
}

// Usage in SongList.tsx:
const el = document.querySelector(
    `[data-song-id="${escapeCssSelectorValue(highlightSongId)}"]`
);
```

Alternatively, avoid `querySelector` with string interpolation entirely by iterating `document.querySelectorAll('[data-song-id]')` with a runtime comparison against `element.getAttribute('data-song-id')`. This sidesteps all CSS escaping concerns.

## Issue 5 — `LocateSongsetsPopover` does not clear stale results on reopen

### Severity: Medium (UX)

### Files

- `delivery/webapp/src/components/audio/LocateSongsetsPopover.tsx:39-71`

### Problem

```typescript
const handleOpenChange = useCallback((newOpen: boolean) => {
    setOpen(newOpen);
    if (newOpen) {
      setLoading(true);
      setError(null);
    }
}, []);
```

When the popover is closed and reopened, only `loading` is reset to `true` and `error` is cleared. The previous `songsets` array is NOT cleared. If the first open fetched 5 songsets and the user then removes the song from all 5 songsets (or the songset is deleted) and reopens the popover, there is a brief window where the stale 5 results are rendered before the loading spinner appears.

Due to React's batching and the asynchronous nature of `setState`, the user may see the old songsets list flash on screen before the spinner replaces it.

### Fix

Clear `songsets` in `handleOpenChange` alongside `loading` and `error`:

```typescript
const handleOpenChange = useCallback((newOpen: boolean) => {
    setOpen(newOpen);
    if (newOpen) {
      setLoading(true);
      setError(null);
      setSongsets([]); // <- clear stale results
    }
}, []);
```

## Risks & Considerations

- **Migration 0019 hand-edit**: drizzle-kit generate will continue to emit broken `CREATE TABLE` and `btree + vector_cosine_ops` SQL if the schema definition for `themeAnchors` is not also fixed (Issue 1 Step B). The hand-edited migration is a one-time fix; the schema.ts change prevents recurrence.
- **highlightSongId state change**: Moving `highlightSongId` from a derived value to local state slightly changes the URL-share semantics. The v2 spec already states highlight is ephemeral and not bookmarkable, so this is aligned with the design intent.
- **CTE scoping**: Adding a user filter to the `item_counts` CTE changes the query plan. Verify with `EXPLAIN ANALYZE` on a realistic dataset that the new plan uses the `idx_songset_items_song_id` index and does not degrade for users with zero matches.
