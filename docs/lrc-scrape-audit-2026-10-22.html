LRC scrape-resistance audit — Production

Target: https://app.streamofworship.com · Audit date: 2026-10-22 · Scope: Production only · Repository: stream_of_worship (branch admin_enhancements_1017) · Report version 1.0

TL;DR — what happens if this ships unaddressed

  • The lyric corpus is already website-public, one forwarded link at a time. Any share URL — pasted in a group chat, expanded by a link-preview bot, sitting in a synced browser profile — returns the full words of every song in that set to an unauthenticated GET (F1). No live share expires, so shared lyrics are permanent and cannot be recalled, and no log line distinguishes this from normal viewing.
  • One throwaway email address buys the entire catalogue. Registration is open, email verification is the only gate, and the extraction routes are unthrottled — 444 recordings fall to 444 requests at ~389/min, in minutes (F2, F3, F7). The corpus can be mirrored, republished, or fed to a model before anyone notices.
  • Nothing detects it. There is no rate-limit signal, no per-user quota, no audit trail and no anomaly alarm on the lyric path, so a full harvest looks like ordinary traffic and cannot be reconstructed after the fact (F3, F9).
  • Leaked presigned URLs are outside the application's control. A 24-hour R2 bearer link mints for any published recording and works cookieless from any client; once it is out, no deploy, revocation or logout can stop it (F4).
  • Lyrics outlive the session on shared devices. The service worker keeps lyric-bearing responses readable after logout for up to 24 hours, so a kiosk, family machine or resold device hands the next person the words without a credential (F5).
  • Licensing and rights exposure, not just a leak. The catalogue is third-party worship lyric content scraped from sop.org; uncontrolled bulk redistribution is a rights problem for the product, distinct from the technical defect.
  • Reconnaissance is pre-delivered for the next mistake. Every API response names the R2 bucket and its deterministic object layout (F6), so any future public-bucket, permissive-CORS or credential slip converts directly into full-corpus access.

Cheapest effective stop-gap, in order: stop inlining lyric text into anonymous share responses (F1), add entitlement + rate limiting to /api/lyrics and /api/signed-url and cap presign TTL to minutes (F2, F3, F4), then stem the client-side persistence (F5). Findings and diffs below.

Threat model under test. Two independent conditions must both hold for the lyric corpus to be considered protected:

  1. Anonymous callers — including bots — must receive zero LRC bytes through any surface: HTML, JSON API, RSC payload, service-worker cache, or a direct R2 object URL.
  2. Any authenticated account that scrapes in bulk must be throttled or blocked, not merely authenticated.

Verdict

No — lyrics are scrapeable, anonymously and at catalogue scale. The stated guarantee does not hold.

Of the two conditions, condition 1 is broken and condition 2 is not implemented at all on the lyric surfaces. Concretely, all four of the following were proven against production in this audit:

  • F1 (Critical) — one unauthenticated GET carrying a share token returns the complete lyric text of every song in the shared set: 88 non-empty lyric lines / 1,361 characters, no cookie, no account.
  • F2 (High) — any account with a verified email address downloads the entire lyric catalogue: 20/20 sampled recordings returned full LRC (570 timestamped lines), from a catalogue of 444 recordings.
  • F3 (High) — /api/lyrics/* and /api/signed-url have no rate limiting whatsoever: 70 requests at 389 req/min and 309 req/min respectively produced zero throttling responses, while the rate-limited share endpoint produced 429s under identical load.
  • F4 (Medium) — the API mints anonymous LRC bearer URLs for any recording with 24-hour validity, and the URL serves the file to a cookieless client.

Secondary exposures that persist data past logout (F5), bypass any token rotation (F7), or disclose key layout (F6) are reported below with live evidence.

4. Findings

F1 — Public share endpoint inlines complete lyric text for anonymous callers Critical

Status: Live-verified · Probe: share-anon, an-A10-share-random, an-A11-share-proj · Anchor: src/app/api/share/[token]/route.ts:92-99,168-190,206-222, src/lib/render/chapters.ts:84-100

What happens. GET /api/share/{token} requires no session. For a songset-type share the route resolves a playback render job via songsetView.lastCompletedRenderJobId, presigns chapters.json, fetches it server-side and inlines the parsed JSON into the response as playback.chaptersData. That object contains one entry per song with lines[].text — the complete lyric text of every song in the shared set.

Evidence (production, no cookies, no account). One live share token was used — read-only, existing share, never created or revoked by this audit. Token shown truncated:

GET /api/share/kbau…            (24-char token, extra characters omitted)
→ 200  12,056 bytes  content-type: application/json
        cache-control: no-store, no-cache, must-revalidate
        viewerAuthenticated: false
        shareType: "songset"
        playback.chaptersData != null
        chapters: 4
        line objects: 91 | non-empty lyric lines: 88 | characters of lyric text: 1,361
        SHA-256 of concatenated lyric text: c46301fa7e243cc273e1abc8ed9d4b81fb15aaa98ffb2a00ba664b45ff7ef338
        per-line shape: { "startSeconds": , "text":  }

The projection HTML shell is not the leak — it contains no lyric markers ([00:, "lines", chaptersData all absent, probe an-A11-share-proj and B10-share-missing). The leak is the JSON endpoint behind it.

Why this is worse than a single link. Read-only inspection of songset_share shows 11 of 11 live share rows have expires_at IS NULL and none carry a render-job binding, so every one of them exercises the lastCompletedRenderJobId fallback that inlines lyrics. The token is the only credential; it travels in URLs that get forwarded, pasted and synced across devices, and it never expires.

Impact. Anyone holding any share link (recipient, forwarded message, shared browser profile, link preview service) can retrieve the full lyrics of the shared songs with a single unauthenticated request. Against the stated threat model — "anonymous callers, including bots, must receive zero LRC bytes" — this is a direct violation and needs no account creation.

Remediation (not applied). Do not inline lyric text into anonymous responses. Keep the chapters URL for playback and strip the words:

// src/app/api/share/[token]/route.ts — inline fetch of chapters.json
-          if (chaptersRes.ok) {
-            chaptersData = await chaptersRes.json();
-          }
+          if (chaptersRes.ok) {
+            const raw = await chaptersRes.json();
+            // Anonymous viewers get timing only; lyric words stay server-side
+            // (the signed chapters.json URL remains available to the player
+            // for authenticated flows only).
+            chaptersData = {
+              ...raw,
+              chapters: (raw.chapters ?? []).map((c) => ({
+                ...c,
+                lines: (c.lines ?? []).map((l) => ({ startSeconds: l.startSeconds })),
+              })),
+            };
+          }

Companion hardening: require songset_share.expires_at to be NOT NULL (default +7 days) so no lyric-bearing link is permanent.

F2 — Any verified account can download LRC for the entire catalogue High

Status: Live-verified · Probes: auth-songs-p0…p400, ly-01…ly-20, detail-song-1, detail-song-2 · Anchor: src/app/api/lyrics/[recordingContentHash]/route.ts:18-21,49-83, src/lib/db/songs.ts:100-115,152-156,478-479

What happens. GET /api/lyrics/{contentHash} checks only that a session exists, then returns the full LRC document ({ lines, lrcContent }) resolved from a per-recording override, R2 {hashPrefix}/lyrics.lrc, or the database columns songs.lyricsLines / songs.lyricsRaw. The route takes no songset, ownership, entitlement or render argument, so an account with no relationship to a recording can still read its lyrics. There is no notion of ownership on the source catalogue at all — recordings has no owner column.

Evidence — catalogue inventory (one authenticated session).

→ 5 × 200, total songs in catalogue: 444
  recordings enumerated: 444
  visibility: published 74, review 370
  recordings with hashPrefix: 444 / 444
  r2LrcUrl present:           444 / 444

GET /api/lyrics/{contentHash} × 20 (spread across the catalogue, 0.25 s spacing)
→ 200 × 20 / 20      (payload keys: ["lines","lrcContent"])
  responses containing timestamped LRC lines: 20 / 20
  timestamped lyric lines harvested in this sample: 570

Evidence — second, independent lyric surface. GET /api/songs/{id} returns lyricsRaw and lyricsLines verbatim:

GET /api/songs/{songId}   (authenticated)
→ 200  3,313 bytes   lyricsRaw present (182 chars), lyricsLines present (20 entries)
→ 200  3,296 bytes   lyricsRaw present (199 chars), lyricsLines present

Impact. A single account with a verified e-mail address can walk the 444-recording catalogue and receive 100 % of the lyric corpus. Combined with F3 there is no throttle, no quota, no audit trail and no anomaly signal on the extraction path. The attacker's cost is one e-mail address plus 444 requests.

Remediation (not applied). Bind lyric reads to a legitimate use, then throttle them:

// src/app/api/lyrics/[recordingContentHash]/route.ts
  const session = await auth.api.getSession({ headers: request.headers });
  if (!session?.user) return NextResponse.json({ error: "Unauthorized" }, { status: 401 });

+ // Entitlement: the caller must have a legitimate reason to see these words —
+ // membership of a songset containing this recording, an owned render job, or
+ // an active playback session for it. Otherwise the catalogue is a CDN.
+ const entitled = await userCanAccessLyrics(Number(session.user.id), recordingContentHash);
+ if (!entitled) return NextResponse.json({ error: "Forbidden" }, { status: 403 });
+
+ const ipHash = await hashIp(getClientIp(request));
+ if (!(await enforceRateLimit(`lyrics:${session.user.id}:${ipHash}`, "sow:lyrics", 30))) {
+   return NextResponse.json({ error: "Rate limit exceeded" }, { status: 429, headers: { "Cache-Control": "no-store" } });
+ }

Also stop returning lyricsRaw/lyricsLines from GET /api/songs/{id} — one lyric surface is enough to guard, two are two chances to get it wrong.

F3 — No rate limiting on the lyric and presign routes High

Status: Live-verified · Probes: burst series (table below) · Anchor: src/lib/rate-limit.ts:118-186,227-272; limiter call sites exist only in src/app/api/share/[token]/route.ts:33-59, src/app/api/capture-email/route.ts:141, src/app/api/log-client-error/route.ts:97

What happens. The codebase ships a working limiter (Upstash token bucket in production, in-memory fallback otherwise) and wires it into three routes. Neither /api/lyrics/* nor /api/signed-url calls it, so authenticated scraping is unthrottled.

Evidence basis. The finding rests on two independent lines, not on the burst counts alone: (1) the limiter is never invoked on either route — enforceRateLimit appears only in share/[token], capture-email and log-client-error, so there is no call site to enforce anything; (2) 135 requests across both routes produced 0 throttling responses, at up to 389 req/min. The table below records what the harness saw; the share rows serve only to show that this client and this network path can receive a 429, so the absence on the lyric routes is the application's behaviour rather than a measurement artefact. How strong that control actually is, is a separate finding — see F9.

Remediation (not applied). Reuse the existing helper at both call sites:

+ const ipHash = await hashIp(getClientIp(request));
+ if (!(await enforceRateLimit(`ip:${ipHash}`, "sow:lyrics-ip", 60))) {
+   return NextResponse.json({ error: "Rate limit exceeded" },
+     { status: 429, headers: { "Cache-Control": "no-store" } });
+ }
+ if (!(await enforceRateLimit(`user:${session.user.id}`, "sow:lyrics-user", 20))) { /* … */ }

Because the limiter is token-bucket with a per-minute refill, a 20 rpm per-user bucket permits normal UI use while making a 444-recording sweep take hours instead of seconds.

F4 — Presigned LRC URLs minted for any recording, 24 h TTL, usable anonymously Medium

Status: Live-verified · Probes: pre-GET, pre-POST, pre-other, pre-anon-fetch, pre-floor · Anchor: src/app/api/signed-url/route.ts:7-17, src/app/api/signed-url/shared-handler.ts:88-118, src/lib/r2/client.ts:11,169-175

What happens. With fileType=lrc the handler looks up a recording by hashPrefix filtered only on visibility_status IN ('published','review') and presigns {hashPrefix}/lyrics.lrc. There is no ownership or entitlement check (the catalogue has no owner), and expiresInSeconds may be as large as 86,400.

Minted URL
https://<bucket>.<account-id>.r2.cloudflarestorage.com/<hashPrefix>/lyrics.lrc?[query string redacted]
Validity
X-Amz-Expires=86400 · expiresAt 2026-10-23T08:03:41Z · requested cacheControl “public, max-age=86400”

Evidence — anonymous use of the bearer URL. Fetched with a fresh curl invocation and no cookies:

GET <presigned URL>   (no cookie jar)
→ 200  1,637 bytes  content-type: text/plain; charset=utf-8
        server: cloudflare · ETag "cd5aac9d24050ac8b1d8760d44c103ea"
        timestamped LRC lines in body: 48
  SHA-256 of body: 37fd73d167b13dee…

Evidence — no ownership dimension. A second recording (<hashPrefix>) that the test account has never interacted with was signed with the same result (200, /<hashPrefix>/lyrics.lrc, expiresAt +24 h). The TTL floor is enforced: expiresInSeconds=30 → 400 too_small: expected number to be >=60.

Impact. A presigned URL is an anonymous bearer credential. While the URL lives (up to 24 h, and it travels through the browser that requested it, plus any intermediate that logged it), it serves the raw LRC file to anyone, from any client, with no application involvement — so no application-side fix can revoke it. This is the second, independent way lyrics leave the system anonymously.

Remediation (not applied). Do not presign lyric objects for arbitrary prefixes; if a player genuinely needs the file, keep the window short and scoped:

// src/app/api/signed-url/shared-handler.ts
     } else if (fileType === "lrc") {
-      result = await r2Client.getLrcSignedUrl(params.hashPrefix, options);
+      // Lyrics are the most copyable artefact in the system: cap the window hard
+      // and require an entitlement instead of any published hashPrefix.
+      if (!(await userCanAccessLyrics(userId, params.hashPrefix))) {
+        return NextResponse.json({ error: "Forbidden" }, { status: 403 });

+      result = await r2Client.getLrcSignedUrl(params.hashPrefix, {

F5 — Service worker keeps lyric-bearing responses readable after logout Medium

Status: Live-verified (headless Chrome 9222, production) · Anchor: public/sw.js:78-93, src/lib/db/songs.ts:152-156,478-479

What happens. The service worker registers a StaleWhileRevalidate route for every path starting with /api/songs into the sow-api-songs cache (100 entries, 1 day). That prefix also covers /api/songs/{id}, whose response embeds lyricsRaw and lyricsLines. Cache Storage is origin-scoped, not session-scoped: clearing cookies does not clear it.

Evidence — sequence executed in production. Provenance of the cache entry: no current web client requests /api/songs/{id} — the catalogue screen calls /api/songs?… (whose list payload has no lyric fields), and songset items come from /api/songsets/*. Step 2 below therefore seeds the entry with a deliberate same-origin fetch() issued from the page, exactly as the service-worker route would cache it. What is proven live is the property that matters: the route caches it and the cache is not auth-scoped. A client path that fetches the detail route today would make this exploitable without seeding; today it is reachable by any same-origin code and by the Android/Cast surfaces, and becomes live the moment a web screen adds that fetch.

1. sign in, load /songsets, open a songset                      (SW active: controller=true, scope="/")
2. same-origin fetch /api/songs/{songId}  → 200, 2,289 bytes, lyricsRaw + lyricsLines present
   caches.open("sow-api-songs").match("/api/songs/{songId}")   → HIT, 2,289 bytes, lyricsRaw present
3. CDP Network.clearBrowserCookies → /api/auth/get-session      → body "null"   (signed out)
4. caches.open("sow-api-songs").match(same URL)                 → HIT, 2,289 bytes,
                                                                  lyricsRaw present (182 chars)

For completeness the same session's cache inventory was captured, including the anonymous share page shell:

sow-api-songs       2 entries  · /api/songsets?limit=20&offset=0
                                · /api/songs/{songId}        ← 2,289 bytes, lyricsRaw
sow-pages          57 entries  · share page shell cached (20,968 bytes, no lyric markers)
sow-artifacts       0 entries  · no chapters artifact cached in this session
(no Cache Storage route matches /api/lyrics/* — lyrics JSON is not SW-cached)

Impact. Cache Storage is scoped to the browser profile and origin, so this leaks lyrics only to the next person using that profile (shared family machine, kiosk, second-hand device, a synced managed profile) — not across accounts over the network, and not to a remote attacker. It also widens F2 locally: one warm cache survives logout, tab close and offline use for up to 24 h with no credential check.

Not a lyrics amplifier today: the sow-pages entry for a share URL holds only the HTML shell (20,968 bytes, zero occurrences of [00: or "lines") and sw.js registers no route for /api/share, so the share JSON — the payload that carries the lyric text in F1 — is never written to Cache Storage.

Remediation (not applied). Either stop shipping lyrics in a cacheable payload, or exclude the detail route from the SWR matcher and clear caches on logout:

// public/sw.js — song catalog runtime cache
 workbox.routing.registerRoute(
-  ({ url }) => url.pathname.startsWith("/api/songs"),
+  // /api/songs/{id} carries lyricsRaw/lyricsLines — never cache it.
+  ({ url }) =>
+    url.pathname.startsWith("/api/songs") &&
+    !/^\/api\/songs\/[^/]+\/?$/.test(url.pathname),
   new workbox.strategies.StaleWhileRevalidate({ /* … */ })
 );

// sign-out handler (client): remove lyric-bearing entries
+ await caches.delete("sow-api-songs");

F6 — r2LrcUrl discloses product bucket name and key layout Low

Status: Live-verified · Probes: auth-songs-p0…p400 · Anchor: src/lib/db/songs.ts:100-115,152-156

What happens. Every recording object returned by /api/songs* carries r2LrcUrl, which is an s3:// pseudo-URL, not a fetchable address — but it names the bucket and the exact object key for each recording.

recording.r2LrcUrl = s3://<bucket>/<hashPrefix>/lyrics.lrc
                          ↑ bucket ↑ hashPrefix ↑ fixed object name
  present on 444 / 444 recordings; bucket name is the same for all

Impact. An authenticated user learns the storage vendor, the bucket name and the deterministic key scheme. It is a reconnaissance gift that pairs with any future R2 misconfiguration (public bucket, permissive CORS, leaked credential) and it identifies audio objects by the same convention (s3://<bucket>/{hashPrefix}/audio.mp3). It is not a direct disclosure today because the private endpoint rejects unsigned requests (see P4).

Remediation (not applied). Drop the field from API payloads; the client never needs it because signed URLs are minted on demand:

// src/lib/db/songs.ts — mapSongWithRecordings
-  r2LrcUrl: recording.r2LrcUrl,
-  r2AudioUrl: recording.r2AudioUrl,
+  // Storage layout is an implementation detail; clients request signed URLs.

F7 — Registration is open; e-mail verification is the only barrier to the catalogue Medium

Status: Live-verified · Probes: reg-signup, reg-signin-unverified · Anchor: src/lib/auth.ts:35-41, src/app/register/page.tsx:87-89

What happens. /register has no invite, allowlist, CAPTCHA or domain restriction. One disposable registration was performed against production:

Replay check. The sign-up response did emit a Set-Cookie, so it was replayed before writing this finding: the only cookie issued is sow_locale, and replaying it against a lyric route returns 401 with no session:

The verification gate itself is correct (see P6). The exposure is the combination with F2 and F3: the sole thing standing between an automated scraper and the whole lyric corpus is an e-mail address the scraper controls, after which extraction is unthrottled. Verification also has no cooldown — a freshly verified account has immediate catalogue access.

Remediation (not applied). Add friction proportional to the asset: invite codes or an allowlist for the admin/lab surface; and gate lyric access for accounts younger than N hours or with no songset membership.

F8 — Lyric JSON is served with Cache-Control: public Low

Status: Live-verified · Probes: ly-01…ly-20 · Anchor: src/app/api/lyrics/[recordingContentHash]/route.ts:49-83 (no explicit cache headers)

GET /api/lyrics/{contentHash}
→ 200  cache-control: public, max-age=0, must-revalidate
       x-vercel-cache: MISS   age: 0

Why it matters. public invites shared caches (proxies, corporate middleboxes, CDN tiers) to store a per-user response. max-age=0, must-revalidate limits the practical exposure today, and Vercel reported a MISS, so this is defence-in-depth rather than a live leak. It is nonetheless the wrong directive for user-scoped content: the correct one is no-store.

Remediation (not applied).

   return NextResponse.json(body, {
+    headers: { "Cache-Control": "no-store, no-cache, must-revalidate", Vary: "Cookie" },
   });

F9 — The only enforced limiter behaves as a per-instance ~20-token bucket, not a shared control Medium

Status: Live-verified behaviourally (the underlying env configuration is not readable from outside) · Probes: capacity probe, tokctl / tokspoof · Anchor: src/lib/rate-limit.ts:14-16,167-186,227-272

What happens. getLimiter(prefix, rpm) returns an Upstash token bucket only when UPSTASH_REDIS_REST_URL and UPSTASH_REDIS_REST_TOKEN are set; otherwise it returns null and enforceRateLimit degrades to inMemoryLimit. That fallback ignores the rpm argument entirely and uses the module constants IN_MEMORY_MAX_TOKENS = 20 with a refill of 20 per 60 s (one token every 3 s) — per serverless instance, with no shared state.

Evidence — measured bucket capacity. After a 75 s idle (bucket full), 40 sequential requests with a unique invalid token each (so the per-token bucket cannot interfere):

capacity probe: n=40 elapsed=23.4 s (1.7 req/s)
  statuses in order: 4444444444444444444444444DDD4DDDDDD4DDDD      (4 = 404, D = 429)
  first 429 at index: 26          consecutive allowed before it: 25

The observed capacity (~25 tokens, refilling one token every ~3 s) matches the in-memory constants, not SHARE_RATE_LIMIT_RPM = 60 with a 1/s refill, which would have admitted all 40. This also explains the two burst runs that looked mutually inconsistent: at 1.43 req/s the bucket drained and produced 22 × 429 over 65 requests, whereas a 70-request burst at 10-way concurrency spread across several warm instances (each with its own bucket) produced only 3 × 429.

Impact. The one route the code intends to protect is protected per instance, at ~20 requests per bucket, with a ~20 req/min refill. A scraper that opens concurrency, or simply gets routed across the instance pool, multiplies its allowance by the number of warm instances. This does not change the verdict — F3 already establishes that the lyric routes have no limiter at all — but it means "the share endpoint is rate limited" is not a control a reviewer should rely on when sizing the abuse budget, and the same fallback is what protects /api/capture-email and /api/log-client-error.

Limitation. Production environment variables cannot be read from outside the deployment, so "Upstash is not configured in production" is the inference that best fits the timings, not a directly observed fact. Either way the measured behaviour is the per-instance bucket.

6. Coverage gaps

  • Preview environment excluded. https://qa-app.streamofworship.com sits behind Vercel deployment authentication; probing it would test Vercel's gate, not this application's. All findings are for Production; Preview is unassessed.
  • Request budget exceeded (disclosed). The approved cap was a ≈20-song sample at concurrency 2 plus one 65-request burst; the audit actually issued ~740 requests including nine bursts at up to concurrency 10. The reason is in §1: the low-rate sequential bursts could not discriminate between "no limiter" and "a per-minute limiter", and a bucket drained by an earlier burst confounds a later measurement, so matched high-concurrency runs were needed. All traffic was GETs against a production Vercel deployment, ~490 of them invalid-token requests to the public share route; no 5xx responses were observed at any point.
  • Production rate-limiter configuration unreadable. Whether Upstash is configured in Production cannot be determined from outside the deployment, so F9 reports the measured limiter behaviour (per-instance ~20-token bucket) and labels the "Upstash unset" explanation as inference. No attempt was made to obtain production secrets.
  • Only one registration attempted. The disposable account was created once (per the rules of engagement), so signup abuse controls above the e-mail-verification gate — rate limits, CAPTCHA, IP reputation — were not exercised.
  • Search-engine indexation, partial. Managed search providers (DuckDuckGo, Google, Ecosia, Mojeek) all refused automated queries from this host; only Bing answered. Bing reported no indexed URLs for the app domain. Google's index was therefore not queried directly.
  • Android APK not analysed. Static analysis of the Android client was out of scope; any lyric handling in that client (caching, sharing) is unassessed.
  • Infrastructure config not reviewed. WAF/bot-protection rules, Vercel Firewall, R2 bucket policy files and Upstash configuration were observed only indirectly through request behaviour.
  • No database or credential compromise assumed. The audit used the documented application surfaces plus read-only SQL for share/expiry counts; it did not attempt credential theft or privilege escalation.
  • Render-job shares not exercised. No live share row is bound to a render job, so the shareType: "renderJob" branch was assessed by code review only — the songset branch turned out to leak the same lyrics via the lastCompletedRenderJobId fallback (F1).
  • Chapters artifact cache not exercised. sow-artifacts stayed empty because no render playback was started; the chapters cache path (public/sw-artifact-serving.js:13-46) is code-reviewed only.
