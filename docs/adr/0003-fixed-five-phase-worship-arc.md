# The five-phase worship arc is a fixed invariant, not a configurable template

The songset constructor orders every Songset against a fixed five-phase liturgical arc — 讚美 (Call) → 感恩 (Thanksgiving) → 敬拜 (Worship) → 奉獻 (Response) → 差遣 (Commission) — derived from contemporary worship-leading literature and the SOP catalog's thematic vocabulary. This is hardcoded in the constructor's source, not a user- or operator-configurable template: the 12-value validation vocabulary maps to phases via `THEME_TO_PHASE`, and per-song-count phase templates (`_THEME_TEMPLATES`) select which phases appear for a given set size.

We chose the arc as a fixed invariant for two reasons. First, it encodes the domain's theological structure: the arc is the point of the product, not an option. Every reasonable worship set expresses it, so making it configurable would add a large decision surface (phase ordering, phase names, per-count templates, worship-liturgy variants) that today has no user making the choice. Second, a fixed arc is what makes the constructor's hard constraints and fitness scoring meaningful — H1 (phase-1 opener, phase 4/5 closer), H7 (phase drops by at most 1 between adjacent songs), and the tempo trajectory all presuppose exactly these five ordered phases. Treating the arc as data would ripple into every one of those rules.

The cost is rigidity: phase templates exist only for 2–5 song sets (2: Call→Response; 3: Call→Worship→Commission; 4: Call→Worship→Response→Commission; 5: full arc), and sets of 6 or more songs currently have no defined template. This is an acknowledged boundary, not a sign the arc is meant to vary. If product need later demands custom arcs (e.g., a prayer-meeting variant that repeats early phases), that would define a genuine configurable template layer and contradict this ADR.
