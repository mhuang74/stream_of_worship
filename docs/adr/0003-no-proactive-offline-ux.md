# No proactive offline UX; the nav surfaces Worship, not a downloads list

Two decisions about how the app behaves around offline connectivity (issue #211 follow-up descope).

**(a) No proactive connectivity banner, no stall-only overlay.** The app never announces connectivity state on the user's behalf. The former red "Offline" banner rendered on any state that was not positively Online — including Unknown while the boot probe was still in flight — so it flashed at every cold start with no real network problem; it is removed entirely. Likewise the controller player no longer surfaces a "playback stalled" overlay after a timeout: a stall on a healthy network is transient and required no user action, so the panel was noise. What remains is the single actionable surface: the hard-error media-failure overlay with its Retry button (backed by host-takeover recovery). Downloaded copies are used transparently — cache-first boot serves the controller document and cached artifacts without asking — and a genuinely failed media load is the one moment the user is interrupted, because that is the one moment an action (Retry, re-download) helps.

**(b) The nav's Worship page (`/worship`), not an Offline page.** The old nav item led to a list of only already-downloaded songsets — a dead end: empty for every new user, and disconnected from the caching action, which lived elsewhere. The route is renamed `/worship` and the page now lists every songset with a rendered lyrics video (fetched page-by-page when online, no hard cap), defaulting to the Ready for Offline Worship filter (songsets with an Offline Copy), with an All toggle, and with each row carrying its own caching affordance (Download for Offline / Re-download for Offline / Remove from offline via SongsetRow). The caching state belongs on the playback surface, and a songset with a rendered video is worshipable whether or not a copy is cached — so the list is organized around worship, not around downloads.

Consequences: connectivity machinery (`useConnectivity`, the health probe, the SW's document routes) is unchanged; the offline redirect target, the controller exit route, and the SW's immortal navigate route all point at `/worship`; the pre-cache helper is `cacheWorshipListDocument`. If a user wants a strictly fresh-copies list, the Ready filter's predicate (`isOfflineAvailable`) can be tightened to exclude stale rows — rejected for now because hiding a stale downloaded copy would strand the user with outdated media and no visible way back to it.
