# Locale is a per-user UI setting resolved in-app, not a URL route

The webapp needs a display-language choice (English or 繁體中文) for Chinese users. We resolved it as a **per-user setting stored in the existing `user_settings` table, read by a client-side locale provider — not via URL-based locale routing.** The locale governs **UI text only**; the song catalog, lyrics, and rendered output are always Traditional Chinese because that is how the catalog and lyrics are stored.

We chose a per-user, non-routed locale for three reasons. First, the requirement is phrased as a *setting* ("a Language setting the user can set"), and the existing settings infra (`user_settings` table, settings API, settings form) already holds per-user preferences behind Better Auth — a locale field slots in with no new persistence machinery. Second, with only two locales (English, 繁體中文) and no need for search-engine crawlable localized copies, a full routing framework (next-intl) and `/en/...` `/zh-Hant/...` path prefixes are weight we don't need; a typed string dictionary plus a React context provider reading the user's saved locale is the right-sized approach. A routing-based locale would also force every route into the locale segment and couple the address to the language, which this product has no reason to do. Third, keeping the catalog and lyrics Traditional-only removes the entire belongs-to-simplified-chinese conversion problem: since only Traditional is supported, song titles render verbatim from the database, and there is no trad↔simp translation step anywhere.

The cost is that locale is a session/account property rather than a URL property — changing it does not change the address, so there is no shareable "in Chinese" deep link, and server-rendered markup (e.g. `<html lang>`) must read the session to reflect the locale rather than deriving it from the path. That is acceptable: this is a logged-in app where the locale is a personal preference, not a public-facing content-locality concern. Pre-login pages default to English.

This is a webapp-only decision. The Android client is a separate surface with its own UI strings and is out of scope; if it later needs a locale, it should be implemented there, not through this provider.
