# Cascade Failover Is Strictly Sequential and Starts With RunPod

ADR 0016 authorized ElevenLabs followed by a Modal-first GPU hedge. Replace that with `cascade-simdps`: RunPod gets `SOW_GLUE_SIMDPS_SECONDS` (default 120) from its own submission, Modal gets the same window after RunPod produced no verified result, and ElevenLabs gets `SOW_GLUE_ELEVENLABS_SECONDS` (default 60) last. The provider selector, deploy scripts and webapp quote are unchanged; the policy name lives in the route's `policy` field and fresh routes are written as version 3.

The hedge in ADR 0016 starts two L4 calls before the first is cancelled, so a slow queue bills twice for one Job. Sequential windows cost at most one GPU call at a time and make the order match cost and latency expectations: RunPod is the cheaper queue, Modal is the fallback for a RunPod outage or queue stall, and ElevenLabs is the last resort. The tradeoff is a longer worst case — RunPod's 120 seconds are always spent before Modal starts — which the two-window arithmetic against the 780-second Lambda budget bounds.

Failover stays durable and one-way, as in ADR 0016: each backend gets at most one submission, the previous backend is marked timed out and cancelled before the next is submitted, and the first verified result supplies the Job's one Glue Take. A failed input-storage put before any attempt exists is free and falls through to the next backend; the same failure after the attempt was persisted re-raises, so the Job takes the ambiguous/paid path instead of double-submitting. A verified-result lookup error never marks an attempt timed out.

Redelivery becomes salvage-only. Recovery reads the persisted result key of each attempt in the worker's fixed backend order (RunPod, then Modal), followed by a possibly billed ElevenLabs compose, and promotes the first verified result; a final read also inspects attempts already marked `timeout`, because a GPU can write its result between the stage's last lookup and its cancellation; it never resubmits and never restarts a window. That order equals submission order for version 3 routes and differs for a version 2 route (Modal was submitted first there), which is harmless: every candidate is an already verified object and only one can become the winner. A redrive therefore cannot spend again, at the cost of failing paid when an in-flight GPU call had not yet written its result. Version 2 routes stay readable under the same salvage rule, so a deploy does not strand in-flight jobs.
