# Gap placeholders are inserted post-LLM, deterministically — not via the prompt

Rendered lyrics videos used to hold the last sung line through long instrumental gaps, leaving the congregation staring at stale lyrics. The analysis service now inserts one intentionally blank, timestamped **Gap Placeholder** line into the LRC after LLM correction, whenever the gap between two consecutive lines exceeds 12 beats (config `SOW_LRC_GAP_THRESHOLD_BEATS`); the placeholder lands 4 beats after the line's end (`SOW_LRC_GAP_PLACEHOLDER_BEATS`). The webapp render path already blanks on empty-text lines, so the screen goes dark over the passage instead of lingering.

We chose deterministic post-LLM insertion over prompt-driven generation because the insertion must be exact (beat-math against transcript cue timings) and stable across LLM outputs — asking the model to emit blank lines would make placement non-deterministic and would also churn the eval bake-off harness that scores prompt variants. A consequence: the LLM never emits these lines, so anything that consumes LRC must tolerate empty-text lines (the webapp `parseLRC` keeps them; the render worker's `parse_lrc` already did). The LRC cache tag bumped `lrc-lang-v4` → `lrc-lang-v5` so re-submitted jobs regenerate. Inserting lines shifts `line_start`/`line_end` indices of subsequent lines in component analysis — the existing workflow of re-running component analysis after LRC regeneration covers this; no code change was needed.

Scope note: the YouTube-transcript LRC path implements this; the Whisper/Qwen3 fallback paths do not (deliberate follow-up).
