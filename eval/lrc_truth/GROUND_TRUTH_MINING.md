## Pairing rule (spec-faithful)

A backup is paired with its successor ONLY when the successor is the
recording's **current** content and `recordings.lrc_source ∈ {manual_upload,
llm_edit}`. Backup→backup successors have no per-version provenance
(`lrc_source` is a recording-level column that only exists since 2026-09-23),
so intermediate transitions are skipped and counted — never paired. Two
machine outputs are never diffed.

**Ladder-order check (gating):** each pair is (newest backup → current). A pair
ships ONLY when the newest official backup's content hash equals the newest
editor-session backup's hash (`{hash_prefix}/backups/lyrics.{ts}.lrc`, written
by `upload_r2_backup` before each editor save) — the same editor session wrote
both, so the backup is the immediate predecessor of the current content and no
intermediate version was lost. Prefixes without an editor-session ladder
(immediacy unverifiable) or with a hash mismatch are skipped with a recorded
reason.

## Backup timestamp caveat (matters for ordering)

Backup keys mix two timestamp sources:

- `lyrics.backup.{wall-clock ms}.lrc` — admin-cli
  (`int(time.time() * 1000)`) and most editor-session saves. Correct order.
- `lyrics.backup.{small values}.lrc` — the analysis service's historical bug
  (`int(asyncio.get_event_loop().time() * 1000)`, `storage/r2.py:406`):
  `loop.time()` is monotonic **seconds** since loop start, so keys like
  `274768205` are loop-uptime ms (~76 h), not wall clock. Ordering within one
  service process is still valid (monotonic), but these keys cannot be dated
  from the key. `is_ms_epoch()` distinguishes the kinds; ordering uses
  object Last-Modified, which is correct for both (Last-Modified is upload
  time — mutable on re-upload, but backup objects are never re-uploaded).

## Anomaly inspection: manual_upload seed negative

`bu_ting_zan_mei_mi_e937a9d3` is the Appendix A "manual_upload — anomaly,
inspect" seed negative. Findings:

1. **The `wrong_text` feedback (2026-09-23T15:09Z, rating `sad`, unresolved)
   predates the manual upload.** The only editor session for this recording
   ran 2026-09-25 00:50 — two days AFTER the feedback. The seed negative is
   therefore a valid must-FAIL anchor for the LRC state at feedback time,
   which is preserved as backup `274798998` (batch backup 2026-09-24
   00:21:49). The current LRC is the post-fix state. **Phase 1/3 must decide
   which state the negative refers to**: if checker output on current content
   PASSes, that is not a checker false-positive but a stale negative —
   maintainer confirmation needed to resolve the feedback row.
2. **The pre-fix content (backup `274798998`) has real defects** consistent
   with `wrong_text`:
   - bridge/chorus blocks over-repeated: `我讚美讚美 不停讚美`,
     `跳舞跳舞 不停跳舞`, `高舉雙手 大聲讚美祢` each appear 6× in the
     pre-fix LRC vs 4× after the human fix (`count_changes` in the dataset);
     the YouTube structured lyrics carry the bridge only 2×. The 09-25 fix
     also added outro lines (`我要讚美 不停讚美`, `大聲讚美`) 0→2 and a final
     `讚美祢` tag 0→1.
   - the 20-silent-second instrumental gaps carried no ADR-0008 placeholder
     lines (0 blanks) — the fix inserted 3.
3. **Canonical catalog text is unusable for comparison**: `songs.lyrics_lines`
   for this song is a single merged line (scraper artifact — all 13 sop.org
   lines concatenated). YouTube `structured_lyrics` is the only usable
   reference (verse 4 / chorus 4 / bridge 7 lines + preamble URLs).
4. **Provenance paradox explained**: `lrc_source=manual_upload` on a review
   song is not a data error — a human uploaded a hand-made LRC, but the
   content still fails (pre-fix: wrong repeats vs the live recording; the
   uploader's own fix later confirmed the text issue). The pairing rule is
   right to include manual_upload successors: this song shows a
   human-corrected fix changing exactly the failure modes (repeated-line
   structure + missing placeholders + outro text) that a checker must catch.

## Implications for Phase 3 (checker validation)

- Real before/after pairs are rare (n=2): they demonstrate failure modes
  (line splits/merges, wrong repeated-line counts, missing placeholders,
  outro text) but are too few to calibrate thresholds. Synthetic corruption
  (Phase 3 sweep) remains the primary calibration path; these pairs are
  ecological sanity checks.
- The 6 youtube_transcript + 1 qwen3_asr seed negatives each have a
  2026-09-24 00:21–00:26 batch backup that preserves their **pre-regen**
  (feedback-time) state; current content differs (post-regen). The same
  stale-negative caveat as the anomaly applies to all 7: if the checker
  passes their current content, resolve with the maintainer rather than
  forcing a FAIL.
